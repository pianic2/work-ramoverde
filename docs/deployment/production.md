# Production deployment

Build `infra/docker/Dockerfile.backend` with target `production` and `infra/docker/Dockerfile.web` with target `production` as separate images. Backend starts Gunicorn as UID 10001; static web is served by unprivileged Nginx on port 8080. Build the web image with a public, HTTPS `VITE_API_BASE_URL` pointing to the versioned API.

For a hardened Compose deployment behind a trusted TLS reverse proxy, set `DATABASE_URL`, `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, `DJANGO_CORS_ALLOWED_ORIGINS`, `DJANGO_CSRF_TRUSTED_ORIGINS`, and `VITE_API_BASE_URL`, then run `docker compose -f compose.production.yaml up --build -d`. The production Compose file publishes backend and web only on loopback, runs with read-only root filesystems, drops Linux capabilities, disables privilege escalation, and provides a bounded writable `/tmp`. PostgreSQL remains an external managed service. Keep the default development `compose.yaml` for writable source mounts and local tooling.

Provision managed PostgreSQL, inject `DJANGO_SECRET_KEY` from a secret manager, set `DJANGO_SETTINGS_MODULE=config.settings.production`, `DJANGO_ALLOWED_HOSTS`, `DJANGO_CORS_ALLOWED_ORIGINS` and `DJANGO_CSRF_TRUSTED_ORIGINS` explicitly, then terminate TLS at a trusted proxy and configure forwarded-proto handling. Run `python manage.py migrate` as a release job before deploying backend workers. Do not run migrations at startup.

Production settings require a PostgreSQL `DATABASE_URL` and HTTPS CORS/CSRF origins. If a product enables S3 storage, build the backend with `UV_EXTRA_ARGS="--extra storage"` and set `S3_STORAGE_ENABLED=true` and `S3_BUCKET_NAME`. Compose also forwards optional `S3_ENDPOINT_URL`, `S3_ACCESS_KEY_ID`, and `S3_SECRET_ACCESS_KEY`; leave credentials empty to use workload identity. The default image stays free of the optional storage dependencies.

Run `python manage.py check --deploy --settings=config.settings.production` in CI with production-shaped placeholder values. The service must have a readiness probe against `/api/v1/health/ready`. Configure backups, restore tests, log retention, upload scanning and provider-specific resource limits outside this template. No cloud credentials are required for development.

Django accepts at most 2.5 MiB of non-file request data, 1,000 form fields, and 20 uploaded files per request by default. Files are moved to temporary storage after 2.5 MiB. Override these values with `DJANGO_DATA_UPLOAD_MAX_MEMORY_SIZE`, `DJANGO_DATA_UPLOAD_MAX_NUMBER_FIELDS`, `DJANGO_DATA_UPLOAD_MAX_NUMBER_FILES` and `DJANGO_FILE_UPLOAD_MAX_MEMORY_SIZE` when the product needs different bounds. `DATA_UPLOAD_MAX_MEMORY_SIZE` excludes uploaded file bytes, so enforce a total request/file size and temporary-storage quota at the trusted proxy or hosting platform.
